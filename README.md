# CMAI Tracker

A progressive web app (PWA) for caregivers. Log each agitated behavior as it happens, and see Cohen-Mansfield Agitation Inventory (CMAI) scores for every 14-day period. Works offline and installs to a phone's Home Screen.

Built by Devin Ferrell for the Hands-On Lab, Old Dominion University (hands-on interview, October 2026).

## What the lab asked for

> "We need to develop a CMAI form app that allows caregivers to record each time they observe a behavior listed in the CMAI, such as kicking or hitting. The app should save each observation and calculate the CMAI scores every 14 days. It should display the total score and individual scores for each behavior to help us track agitation patterns over time."

## The one design decision that matters

The CMAI isn't a count. It's a caregiver's look-back rating (1 to 7) of how often each behavior happened over the last two weeks (manual p.2, p.5). This app counts events, so it converts each 14-day count into a 1 to 7 rating with a written, tested rule. The caregiver then confirms or corrects those ratings at day 14. The full rule is in [docs/scoring-spec.md](docs/scoring-spec.md). Every choice that still needs the lab's sign-off is tracked in [docs/review-register.md](docs/review-register.md).

## What it does

- **Log:** 29 buttons, one per CMAI behavior, grouped the way the manual groups them. Each button shows a short description in our own words with the manual page for the full definition, plus an ⓘ button with what does not count where the manual excludes things. Jump chips go straight to a behavior group, and a patient banner on every screen shows who is being logged for. You can undo a tap, set when it happened (5 to 60 minutes ago, or a clock time), mark the time as approximate, or note what happened just before. "Recent logs" lists the last 24 hours so a time can be fixed or a mistaken log deleted, with undo. On a quiet day, "Nothing to log today" records that the day was quiet rather than missed.
- **Scores:** per-behavior CMAI-based (app-derived) ratings for each period, agitated or not for three behavior groups (manual thresholds), group averages over time, the total (labeled secondary), and when in the day behaviors happen.
- **Day-14 review:** confirm or change each rating, including codes 8 (prevented) and 9 (not applicable).
- **Data:** a welcome screen on first run; pseudonymous patient codes only, with delete (confirmed); six weeks of demo data, which can be removed; a backup file (JSON) that can be restored on this or another phone, plus CSVs (including check-ins and unlogged days per period); an install button where the browser supports it; Display settings for light, dark and high contrast; and a short page on how ratings are worked out.

## Run it

```bash
npm install
npm test          # 38 tests, including 19 hand-scored cases from docs/test-cases.json
npm run dev       # http://localhost:5173
npm run build     # production build in dist/, with service worker
npm run preview   # serve the build at http://localhost:4173
```

Deploy: every push to `main` runs the tests, builds, and publishes to GitHub Pages (`.github/workflows/pages.yml`). Pull requests run the tests and build only.

## How the code is organized

| Folder | What's in it |
|---|---|
| `src/scoring/` | The CMAI items and the scoring engine. Pure functions, no screens or storage, so they can be tested and reused on other platforms. |
| `src/data/` | Local storage (IndexedDB through Dexie), demo data, export, restore and delete. |
| `src/ui/` | The four screens. |
| `docs/` | Scoring spec, hand-scorable test cases, research notes, agreement study materials (`agreement/`), audit reports (`audits/`), usability materials (`usability/`). |
| `tests/` | Runs the engine against every case in `docs/test-cases.json`. |

## For the other platform builds

`docs/scoring-spec.md` and `docs/test-cases.json` don't depend on any platform. If the iOS and Android versions pass the same cases, all three apps give the same scores for the same logs.

## Privacy

Data stays on the device until someone presses Export. Patients are codes, never names. This is a prototype: see the IRB note below before any real use.

## How this was built

Most of the code was written by an AI coding agent (Claude) working from my written requirements. I wrote the requirements and the scoring spec, designed the test cases, reviewed the code, and made the release decisions. The test cases' expected answers were written by hand from the spec, not generated by the engine, so the tests check the engine against the spec.

## Review register

This is an interview prototype. Lab sign-off on scoring choices, author permission and IRB review come later, if the lab adopts the app. Until then, every open item is tracked in [docs/review-register.md](docs/review-register.md). Each one has an ID, the default this build uses, its evidence, who signs off, and the gate it belongs to (G0 interview demo, G1 lab adoption, G2 real-world use). Rule changes are recorded in its decision log.

## Proposed, not built

Each waits on a lab decision or the agreement study (register section F).

- **Day-14 prompt for likely 7s:** when a behavior has 3 to 6 clustered days, ask at review whether it happened several times an hour on most days.
- **Medication-change marker:** mark the date of a medication change on the charts, with a baseline period logged before it.
- **Rater print view:** 14-day per-behavior counts on one page, for a rater's CMAI interview.
- **Target behaviors:** pick 1 to 3 behaviors that matter most and sort them to the top.
- **MCID reference band:** show a total change next to published meaningful-change values (Liu 2025; Meunier 2024).

## Design

Visual design follows public health design systems (NHS, USWDS), Apple and Material patterns, and research on older users and patient identification. Light and dark mode switch from the sun/moon button at the top, or under Data, Display, where "Match phone" (the default) follows the phone's Dark Mode. High contrast is there too, and turns on by itself when the phone's Increase Contrast setting is on. Palette, type and the reasons for each are in [`docs/design/design-brief.md`](docs/design/design-brief.md).
